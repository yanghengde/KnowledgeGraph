# HistoryMainline → HAS_SPEC → Spec

> **产品线**: 通用 (无产品线)
> **基数**: MANY_TO_ONE
> **生成时间**: 2026-08-04
> **来源**: 物理 Schema + LLM

## 关系说明

在 Siemens Opcenter (Camstar) MES 中，HistoryMainline 是所有交易历史（Transaction History）记录的基类对象，记录了生产执行过程中每一次关键事件的完整快照，包括物料（Container）、工序（Operation）、资源、操作者、时间戳以及本次执行所依据的工艺规格。HAS_SPEC 关系正是连接"历史执行记录"与"执行所依据的 Spec 实例"的桥梁，它确保每一条历史记录都可以明确追溯到当时使用的工艺定义。

该关系为 MANY_TO_ONE 基数：同一个 Spec 实例（例如某个已发布的工艺规格版本）可以被成百上千条 HistoryMainline 记录引用，而每一条历史记录只能关联一个 Spec。在通用（无产品线）的 Opcenter 建模场景中，这意味着只要一个 Spec 被正式发布（Released）并在车间执行，后续所有以该 Spec 为依据完成的操作都会被持久化到 HistoryMainline，并通过 HAS_SPEC 指向该 Spec 的快照。

这条关系是 Opcenter 完整追溯体系的核心环节，回答了"这批产品当时是按什么规格做的"这一关键审计问题。无论是工艺变更调查、质量异常分析，还是批次追溯，用户都可以从一条历史记录直接跳转到对应的 Spec 定义，查看当时的工序步骤、物料清单与参数要求，从而将"执行历史"与"规格定义"完整串联。

## 业务场景

### 何时需要配置此关系？

1. **工艺合规与审计追溯**：企业需要确认某一批次产品在生产过程中是否严格遵循已发布的工艺规格。配置 HAS_SPEC 后，既可以按历史记录反查规格，也可以按规格反向查询所有执行过该规格的历史记录，形成闭环追溯。

2. **规格版本变更管理**：当 Spec 发生升版（例如从 V1.0 升到 V2.0）时，历史记录仍保留对旧版本 Spec 的引用。这样在追溯时能够清楚区分"执行时所用的规格版本"与"当前最新发布的规格版本"，避免因版本覆盖而产生混淆。

3. **质量异常与偏差调查**：当产品出现质量缺陷时，质量工程师需要回溯每道工序所使用的 Spec 及其参数。通过 HAS_SPEC，可以快速从异常历史记录定位到对应的规格，判断问题根源是规格设计缺陷还是执行偏差。

### 通用 (无产品线) 典型示例

以离散制造中"机械零件 CNC 加工"工序为例：

1. 在 Opcenter 建模环境中创建 Spec，命名为 `MACHINING_OP10_V2.1`，绑定工序 `OP10_CNC_TURNING`，并定义关键参数（主轴转速、进给率、切削深度）。
2. 将该 Spec 发布（Change State → Released），使其可供车间执行使用。
3. 车间操作员在执行容器（Container）的 Start 操作时，从规格列表中选择 `MACHINING_OP10_V2.1` 作为本次执行依据。
4. 系统在执行成功后生成一条 HistoryMainline 记录，并自动写入 HAS_SPEC 引用，指向 `MACHINING_OP10_V2.1` 这条 Spec 实例。
5. 后续在历史查询界面中打开该记录，即可看到 Spec Name 字段显示为 `MACHINING_OP10_V2.1`，并可一键导航到该 Spec 的完整工艺定义，包括绑定的工序、物料和参数标准。

## 配置要点

- HAS_SPEC 关联由系统在交易（Transaction）执行时自动写入，无需在建模时手动创建关系实例；前提是 Spec 的状态必须为 Released，否则无法被选中作为执行依据。
- 该关系保存的是"事务发生时选中的 Spec 实例"，而非最新版本规格；后续规格升版不会影响已写入的历史记录，这是保证审计一致性的关键设计。
- 注意区分 Spec 与当前版本：如果同一个逻辑规格存在多个版本，HistoryMainline 指向的是具体的版本实例（如 V2.1），而不是抽象的逻辑规格分组。
- 在多站点（Multi-site）部署中，Spec 通常在上层节点建模，而历史数据存储在执行站点。HAS_SPEC 作为跨站点引用，要求 Spec 的 Name 在站点范围内保持唯一，避免引用歧义。
- 在开发自定义页面或业务规则时，如需读取该关联，应使用 Opcenter 提供的 `GetSpec()` / `GetHistory()` 等 API 方法，不要直接依赖物理字段判断，以保证缓存与持久化的一致性。
- 当 Spec 被作废（Obsolete）或归档时，历史记录仍保留对它的引用；但应避免物理删除 Spec，否则历史记录中的规格信息将变成无效引用，破坏追溯链的完整性。
- 反向查询（从 Spec 查全部历史）不属于建模配置范围，需要通过查询面板（Query Panel）或报表工具基于该关系的引用字段进行过滤，建议在相关字段上建立索引以提升效率。

## 常见问题 FAQ

**Q: 多条历史记录引用同一个 Spec 是否会产生数据冗余或性能问题？**
A: 不会。HAS_SPEC 为 MANY_TO_ONE 关系，HistoryMainline 仅存储 Spec 的引用标识（Name 或 ID），不会复制 Spec 的完整内容。因此十万条历史记录引用同一个 Spec 也不会造成规格数据的冗余；按规格反查历史时，应确保该引用字段已建立索引以优化查询性能。

**Q: 当 Spec 升版后，旧的历史记录会自动更新指向新版本吗？**
A: 不会。HAS_SPEC 保存的是事务执行时刻所选择的具体 Spec 实例，系统不会在规格升版后改写任何历史记录。这正符合追溯需求——历史记录反映的是"当时执行依据的规格"，而不是"当前最新的规格"。

**Q: 为什么在历史查询界面中看不到 HAS_SPEC 对应的列？**
A: HAS_SPEC 是一个对象引用关系，不是扁平化的普通字段。在 Opcenter 的标准历史查询网格中，需要通过"Spec" 列或自定义查询面板来展示；如果使用自定义查询，需要确保查询涉及的 Data Transfer Service 已包含该关系，并将 Spec 作为命名对象（Named Object）引入。

**Q: 是否所有类型的 HistoryMainline 记录都会写入 HAS_SPEC？**
A: 不是。由 Spec 驱动的执行类事务（如 Start、Complete、Rework、Hold、Split 等）所生成的历史记录会写入 HAS_SPEC；而纯数据维护操作、与规格无关的参数调整或系统内部事务则不会设置该关联。判定依据是交易执行时是否指定了 Spec 作为输入参数。
