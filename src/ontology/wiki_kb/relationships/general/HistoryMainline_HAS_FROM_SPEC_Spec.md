# HistoryMainline → HAS_FROM_SPEC → Spec

> **产品线**: 通用 (无产品线)
> **基数**: MANY_TO_ONE
> **生成时间**: 2026-08-04
> **来源**: 物理 Schema + LLM

## 关系说明

HistoryMainline 是 Opcenter (Camstar) MES 中执行历史的核心实体，它记录了生产过程中一次完整执行的痕迹——包括工序执行、数据采集结果、异常信息、操作者行为等。Spec（规格）则是预先定义的、经过审批的标准模板，明确了“应当如何执行”的步骤、参数与采集项。HAS_FROM_SPEC 关系将“实际发生的历史”（HistoryMainline）与“预期定义的来源规格”（Spec）建立起单向引用，语义上表达“这条执行历史来源于哪一个批准规格”，从而在时间维度和版本维度上回答追溯中“当时按什么标准干的”这一关键问题。

在通用（无产品线）场景中，该关系属于运行时自动建立的对象关联。当作业人员通过“执行终端”、“工单开始”或“生产派工”等入口启动一个生产执行时，系统在 HistoryMainline 下生成相应的历史记录，同时根据启动时所选取的 Spec（例如工单规格、操作规格、流程规格）自动写入 HAS_FROM_SPEC 引用。该关系的基数为 MANY_TO_ONE，即一个 Spec 可以被大量历史执行记录所引用，而一条历史记录在其生命周期内原则上只关联一个来源 Spec；这是因为同一份已批准规格会被反复执行多次，每次执行在数据库中都形成一条独立的 HistoryMainline。

从建模角度理解，该关系是“计划-执行-追溯”闭环中的版本锚点。没有这条关系，历史数据只是一堆独立的工艺数据点，无法回答“依据哪个版本的规格完成”的合规性问题；有了这条关系，用户在追溯界面可以顺藤摸瓜地查看来源规格的内容，并且可以在规格版本更新、作废后仍然还原当时唯一的基准。同时，企业质量管理、生产审计和持续改进业务都依赖该关系将实际执行结果与预期标准进行精细化对比。

## 业务场景

### 何时需要配置此关系？

该关系通常不需要管理员手工配置，而是通过启动执行事务时选择规格而自动建立。但在以下业务场景中，建模人员需要显式关注并验证其存在与正确性：

1. **启动生产执行时要求绑定批准规格**：车间用户在开始生产时选择“流程规格”或“操作规格”，系统据此生成主历史记录并挂接 HAS_FROM_SPEC，保证每条执行历史都有可追溯的标准来源。
2. **合规审计与偏差追溯**：当出现质量偏差或客户投诉时，需要从 HistoryMainline 反查来源规格，确认实际执行步骤、参数采集项是否与规格一致，从而定位是“执行偏差”还是“规格缺陷”。
3. **规格多版本管理下的回溯**：同一规格会因为工艺改善而升版，已完成的执行历史必须保留旧版规格的引用关系，保证审计时看到的是当时的规格版本，而不是最新版本。

### 通用 (无产品线) 典型示例

以下以一个“返修工序执行并关联来源操作规格”的场景为例，说明如何通过该关系建立完整的执行历史追溯链。

**前置条件**：已在 Model 配置中创建名为“OP-Repair-01-返修操作”的 Operation Spec（操作规格），在规格中定义了返修步骤、采集参数“返修温度”、以及返修后的质量验证项，且规格状态为“已发布”。

**操作步骤**：

1. 在 MES 客户端中打开“操作执行”或“工序返修”事务界面。
2. 选择待返修的容器（Container），系统自动加载其当前工艺路径。
3. 在“来源规格”（From Spec）字段中选择已发布的 “OP-Repair-01-返修操作” 规格。该规格被引用为本次执行的标准依据。
4. 启动返修执行。系统在 HistoryMainline 中创建一条主历史记录，自动将 HAS_FROM_SPEC 指向所选择的规格，同时生成该操作的子历史记录并挂接操作步骤。
5. 执行过程中，操作员按规格界面提示录入“返修温度”等数据采集值，这些数值保存在历史记录的数据字段中。
6. 执行结束后，打开“执行历史查询”界面，选择刚才的历史记录，在“来源规格”属性中即可看到所关联的规格名称、版本及发布时间。
7. 质量人员后续通过该历史记录直接跳转至规格视图，逐项比对实际采集值与规格定义的目标范围，完成质量判定。

在这个示例中，HAS_FROM_SPEC 并不是一个需要预先配置的界面字段，而是在步骤 3 中由执行事务依据所选规格自动落账的关系。管理员需要在建模器中确认执行事务的“规格选择”参数已正确绑定到数据源，且该字段对终端用户可见且必填，从而在源头保证关系一定被写入。

## 配置要点

1. **依赖执行入口而不是手工维护**：HAS_FROM_SPEC 关系应在启动执行的标准事务（如 Start、Execute Operation、Process 相关事务）中自动生成，不建议在自定义建模中手工创建；否则容易出现历史记录无来源规格或来源错误的脏数据。
2. **来源规格字段必须在执行界面可见且可设**：在对应的执行事务的 DataGrid 或 Form 属性中，必须显式暴露“From Spec / Source Spec”字段，并且建议将其设为必填（Required），从入口上保证不允许无规格执行。
3. **规格版本策略决定追溯精度**：由于一条历史记录固定引用一个规格版本，配置时不要将规格 ID 设计为覆盖全部版本；应启用版本化管理，避免升版时覆盖同一个规格记录而让历史记录引用错误版本。
4. **注意 Spec 类型和 HistoryMainline 子类型之间的匹配**：例如 Operation Spec 应关联 Operation History，Workflow Spec 应关联对应的 Workflow 执行历史，不要在自定义建模中将不同类型的规格挂到不匹配的历史记录上。
5. **使用同一规格多次执行不会造成冲突**：MANY_TO_ONE 基数下，一个规格可对应多条历史记录；在界面查询和报表设计中应基于规格 ID 做分组聚合，而不是对一对多关系做相等的行匹配，否则会产生重复计数。
6. **删除规格需谨慎**：如果规格已经被历史记录引用，物理删除规格将导致历史记录出现空引用；建议规格采用“作废”逻辑而非物理删除，并通过生命周期状态过滤来避免新业务继续使用废弃版本。
7. **在自定义历史查询中应保留该关系的默认过滤条件**：当开发人员为 HistoryMainline 建立自定义视图或报表时，应默认将 Spec 名称和版本作为显示列，并支持按版本时间戳过滤，以保障审计场景下可按时间与版本准确定位来源规格。
8. **关系字段的本地化与描述信息应补齐**：在建模器中为“来源规格”补充清晰的字段帮助文本，方便车间操作员在执行终端理解其含义，避免误选为“目标规格”或其他规格字段。

## 常见问题 FAQ

**Q: 如果规格在历史记录产生之后被重新发布或作废，历史记录中关联的规格会被自动更新为最新版本吗？**
A: 不会。HAS_FROM_SPEC 关系在历史记录创建时一次性建立并固化，指向的是当时选择的规格版本对象；后续规格升版或作废操作不会影响已存在的历史记录。这一设计保证了历史数据的时间一致性，因此在追溯时看到的是“执行当时的规格版本”，而不是“当前最新的规格版本”。

**Q: 系统中是否存在一条 HistoryMainline 记录完全没有 HAS_FROM_SPEC 关联的情况？**
A: 理论上存在，例如通过后台 API 手工创建历史记录且未指定来源规格时，或者执行事务未经过正规入口而是通过非标准的自定义操作直接生成记录时。但这种情况不符合审计要求，因此建议通过建模约束将执行事务中的来源规格字段设置为必填，并通过数据校验定期扫描空规格的历史记录。

**Q: 在自定义页面或查询中，如何正确区分“来源规格”和“当前工序的规格”？**
A: “来源规格”指的是创建历史记录时实际执行所依据的规格，是运行时属性；而“当前工序的规格”是主数据中当前工艺路线关联的规格，属于主数据属性。两者的值可能因规格升版而不一致。在查询设计时应始终优先读取历史记录上的来源规格属性，而不要从当前工序主数据间接推导，否则会得到错误的追溯结果。
