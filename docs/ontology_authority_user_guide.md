# 本体目录与差异合并

入口：制造语义模型 → 本体目录与差异审阅（默认页）。

## 日常操作

1. 默认展示 16 个公共核心候选。切换“全部本体”可搜索全部类，或选择“待确认与导入候选”。目录不依赖 Neo4j，可在建模库离线时继续整理。
2. 打开模型卡，查看来源、业务定义和物理主键候选。选择权威来源，补充业务中文名、所属领域和业务定义。
3. 对类型冲突明确选择一个来源。物理外键应采用 Navigation，选择错误会阻止确认。
4. 点击“预览合并结果”，检查属性差异、完整属性、关系及未匹配物理字段的扩展属性。默认保留各来源独有属性与关系；同类型元数据采用所选来源优先。来源文件不删除。
5. 确认合并后生成权威修订号。点击“同步权威版本到建模库”，再通过原有模型工作区、校验与发布流程更新 Graph Studio。确认权威版本不会自动激活发布版本。

## 再次导入 CSV

上传物理表和字段 CSV，分析并选择对象后提交候选。旧兼容入口也走相同候选流程，不再直接写入 Neo4j 或 csv_business_import_ontology.json。候选进入模型卡，与已有来源一起预览；重复的同内容提交复用候选记录。已接受的同内容候选不会再次列入待办。

新的物理类若未匹配本项目只读物理事实文件，会在预览中阻止确认，需要先核实事实来源，不能仅凭上传内容自动建立权威模型。

## 数据与状态

- “待确认”：还没有权威快照；旧本体和已有发布仍保持原状。
- “已确认，待同步”：PostgreSQL 已保存权威快照，建模库还未同步该修订。
- “已同步建模库”：该修订曾成功写入建模库。它不是持续的实时一致性探测；外部手工修改需重新同步。
- “来源变化，待复核”：确认后本地定义发生改变，需要重新审阅。已确认快照仍保留。
- 当前问数版本列来自 Graph Studio 实际发布层，未发现与零条数据分别显示；源名重命名为不同发布类名时，该列不会推测映射。

## 开发与运维

控制面新增 graphsync.ontology_authority、ontology_authority_revision、ontology_import_proposal 三张表。通过 sql/ontology_authority_postgres.sql 初始化；控制面初始化和首次使用均可幂等建表。权威模型快照、差异及历史存放 PostgreSQL，不保存连接密码。

确认请求要求匹配来源指纹与服务端预览摘要。保存快照、历史修订及已接受候选在同一事务中完成；并发确认、候选提交和本体批量加载使用同一 PostgreSQL advisory lock。源文件在工具外发生编辑时，过期预览会拒绝提交。

Neo4j 单类同步使用一次写事务，先核实关联终点，失败保留 PostgreSQL 权威版本供重试。控制面在 Neo4j 成功后标记同步；跨库提交异常可能导致“已写建模库但未标记”，可幂等重试。同步不会删除建模库已有的额外属性、额外关系或业务数据。

完整本体加载器会用已确认快照替换对应重复声明，避免旧导入文件覆盖权威定义。加载器现在依赖 PostgreSQL 控制面，不可在控制面不可用时跳过权威裁决继续加载。批量加载原有分批写机制保留，失败后不标记成功，可重新执行。

本次提供治理工具，不自动替用户裁决 318 个重复类，也不自动发布全部 593 个类。历史修订可查看，尚未提供一键回退按钮；历史快照保留在控制面并应纳入数据库备份。
