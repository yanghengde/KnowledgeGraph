# Camstar → Graph Studio 流程简化评审

评审日期：2026-09-05。依据当前工作区代码、只读物理 CSV 和现有测试；未连接生产数据库、未实际操作浏览器或发布 Graph Studio。本文中的优化均为待实施建议。

## 结论

项目已经具备映射编译、发布本体、属性投影、数据质量、不可变数据版本、增量同步、Graph Studio 发布与验收等基础能力。主要瓶颈是用户必须把业务意图翻译成多份技术配置，并且直到后面的数据门禁才发现前面的选择不可执行。

建议主线改为：**选择业务场景 → 确认推荐对象/字段/关系 → 查看真实样本图 → 发布并持续更新**。后台保留现有治理与版本边界，前台由一个可恢复的发布计划贯穿全过程。

优先做一个“制造订单与产品”场景闭环，再扩展工艺、设备、质量；不要以全库本体映射率或画布节点数量作为首版成功指标。

## 当前链路与可复用能力

1. `src/ontology/authority.py` 与 `OntologyDirectory.tsx`：来源差异审阅、权威定义与同步建模库。
2. `inventory.py` / `catalog.py`：物理元数据、属性解析、关系外键候选与人工 override。
3. `publish_ontology.py`：独立发布工作区、属性裁剪、关系用途、建议批次撤销、冻结/激活版本。
4. `graph_profile.py` / `repository.py`：实例范围、对象角色、关系扩展、数据契约。
5. `attribute_projection.py` / `row_scope.py`：关联属性合并、实例范围控制。
6. `curation.py` / `materialization.py` / `data_sync.py`：质量预览、不可变对象/关系版本、数据同步与调度。
7. `deployment.py` / `continuous_sync.py`：制品、路由、环境晋级、发布与 SPARQL 验收。
8. Graph Studio 查询和问答能力：可作为业务验收入口。

源本体、目标模型、数据版本、目标部署有不同生命周期，保留这些边界有价值；用户不必逐个页面手动协调它们。

## 建议的四步操作

### 1. 选择业务场景

默认显示“订单与产品”“产品与工艺”“设备与生产位置”等场景卡片，而不是全库节点画布。第一期只交付经过验证的订单与产品模板，其他场景不要伪装成已就绪。

用户选择业务目的、源连接和数据范围。源本体权威定义存在冲突时，只处理本次选择依赖到的冲突，不要求先清理整个目录。模板按源 Schema 指纹和版本校验，无法适配时生成差异待办。

### 2. 确认推荐图谱

以对象卡片为主，图画布为辅。每个对象同时呈现中文名称、用途、推荐字段和关系、可用数据状态。用户只需做保留、去除、替换或补充。

字段分组：

| 分组 | 默认行为 | 原则 |
|---|---|---|
| 身份与连接依赖 | 后台保留；通常不作普通业务属性展示 | 完整物理主键、关系外键、增量水位、投影连接键；URI 不由可变名称构造 |
| 业务展示 | 按场景推荐 | 名称、编码、说明、版本、关键状态，依据已验证映射 |
| 分析字段 | 可选 | 数量、时间、分类等与业务问题有关的字段 |
| 系统/稀疏字段 | 默认不展示 | 系统设施字段、对当前问题无用字段；采样为空只是建议依据，不能据此永久删除 |
| 关联扩展字段 | 提供“作为属性加入” | 通过现有属性投影契约合并，不要求用户先学习 Join 配置 |

字段卡片应包含：业务说明、源表列、数据类型、脱敏样本、采样非空比例、选择理由。采样必须记录范围、数量、时间、超时与数据版本，不把采样统计写成全量统计。

关联表的处理方式由数据基数和业务含义共同决定：一对一扩展可推荐投影；独立生命周期对象保留节点；一对多不能直接压成单值，需明确列表、聚合或保留节点的策略。版本化对象要分清 Base 与 Revision，先核对实际物理键和语义。

关系卡片应直接解释：例如“订单 → 目标产品”和“订单 → 起始产品”，附完整 Join、方向、基数、依据、采样命中/缺失/多匹配、预计增加的上下文规模。没有业务确认时，物理可连接也不等于语义已确认。

### 3. 查看真实样本图

从用户指定的少量真实订单出发，按选定关系抽取受控闭包。用固定主键集合、索引和查询预算约束读取，不能简单给大表全扫描查询加一个展示上限。

在同一界面显示样本节点与连边、字段值、源记录对照、待确认项、预计发布变化。“元数据关系图”和“真实实例图”必须明显区分。预览复用正式发布的映射、转换、URI、投影和过滤逻辑，避免两套语义。

用户只处理少数不可推断问题，例如两条 Product 外键选哪一条、必需关系缺失怎么办、扩展属性多值怎么办。问题应能在卡片内解决，不跳回技术配置表。

### 4. 发布与持续更新

发布页只有一个明确的下一步动作，并展示当前阶段、目标、计划差异和恢复方式。后台自动准备模型冻结、契约、质量、数据版本、RDF 和目标制品；遇到需要角色确认的动作停在具体可审阅结果上。

初次发布与日常数据更新分开：模型未变时复用已批准模型和配置；模型发生变化时仅审阅变化及影响。后端继续执行幂等、防重叠、不可变版本、回滚和验收后推进相应 checkpoint。接入检查点与目标发布检查点保持各自语义。

完成页给出 Graph Studio 入口、真实对象/关系数量、目标版本、最后更新时间，以及可直接运行的业务验证查询。仅生成文件、冻结本体或激活内部数据版本，均不能显示为“Graph Studio 发布成功”。

## 实施设计

建议新增轻量的服务端 `publication_plan` 应用服务，封装现有模块，不再另建一套对象模型或通用审批系统。持久化于 `graphsync`，复用已有工作区和版本实体。

计划至少绑定：profile/job/route、源连接和 Schema 指纹、catalog snapshot、源本体修订、workspace revision、字段/关系选择、投影与范围策略、质量证据、模型与数据 release、计划 hash。

同一份选择经编译派生：发布本体 + 数据契约草案 + 关系契约草案 + 隐藏抽取依赖 + 同步策略候选。生成候选不自动获得生产审批。

推荐接口职责（名称为建议）：

- `plan`：生成差异、证据、预估规模与阻断项，不发布。
- `preview`：执行有预算的真实实例预览，并绑定计划 hash。
- `apply-draft`：幂等保存选定草案配置，记录进度与补偿；跨 PostgreSQL/Neo4j 不能假设单库事务原子性。
- `publish`：交给持久化执行器续做，复用现有审批、版本与部署能力。
- `status`：统一返回阶段、阻断项、下一步和输出链接。

阻断项采用稳定结构，例如 `code/entityId/fieldId/evidence/action/owner/severity`。服务端在每次确认与执行时检查预期 revision/hash；修改字段、来源、关系或范围后，旧预检必须失效。

关系证据等级建议：物理键唯一且业务模板已确认；物理可验证但语义待确认；多候选；缺少来源。不要把简单路径分数显示为准确率。AI 可解释字段、翻译名称、建议场景，物理键、Join 和类型仍以 CSV 及实际库核验为依据。

## 首个闭环：制造订单与产品

本次只读核验 `docs/Database_Fields.csv` 确认：

- `MfgOrder.MfgOrderId` 是物理主键。
- `Product.ProductId` 是物理主键。
- `MfgOrder.ProductId → Product.ProductId` 与 `MfgOrder.BeginProductId → Product.ProductId` 是两条不同物理外键。
- `Product.ProductBaseId → ProductBase.ProductBaseId` 有明确物理来源。

因此首版可围绕订单和产品开始，按确切命名来源决定是否通过 ProductBase 提取显示属性。不能先假设 Product 表一定直接包含 ProductName，也不能把两条产品外键合成一条无差别关系。“目标产品/起始产品”作为业务语义需与现有契约和业务人员确认。

首版验收：选一组可复现的订单 ID，核对 Graph Studio 中订单、两种产品关联、显示属性和源记录；修改一条源记录后验证更新；删除、空引用、模型改字段和发布失败各验证一次恢复语义。此处是待执行验收计划，不是当前环境验收结论。

## 实施顺序与完成标准

| 阶段 | 交付内容 | 完成标准 |
|---|---|---|
| P0：统一选择上下文 | profile/job/route 显式绑定、稳定源 ID、完整版本差异、复合键支持 | 多 profile 不串线；目标改名不丢源映射；复合键记录不会碰撞 |
| P1：订单产品最小闭环 | 一个模板、统一计划、自动草案、字段分组、关系证据、真实样本预览 | 从新草案到 Graph Studio 不需手工填契约或原始 SQL；歧义在当前步骤解决 |
| P2：发布编排 | 持久化执行、结构化待办、失败续做、统一发布完成页 | 关浏览器后任务可继续/恢复；同一计划重复执行不重复建 Dataset；失败不错误推进发布 checkpoint |
| P3：通用化 | 工艺/设备等模板、投影推荐、源变更影响、增量更新 | 模板在不同 Camstar Schema 下明确适配/拒绝，已批准规则可复用 |

时间应在第一期模板和在线源库基线验证后估算。建议先完成上述窄范围交付，再扩大模块覆盖。

可测量目标：四个主步骤；普通业务人员不输入 SQL/JSON；同一字段只选择一次；每个推荐关系可查看证据；明确区分本体类数量和实例数量；每次成功发布至少通过一组业务路径核对。操作耗时和人工确认次数先记录现状，再设量化下降目标。

## 验证范围与限制

本次执行现有测试：catalog、publish_ontology、graph_profile、attribute_projection、data_sync、platform_stages、inline_publish，共 **99 passed in 5.38s**。覆盖核心计划、模型与部分发布逻辑，但不能证明当前线上连接、权限、数据量和 Graph Studio 运行状态。

现有 `docs/code_review_graphstudio_sync.md` 是历史评审，部分代码已演进；例如当前 deployment 已有加锁入口和失败重试支持，不能直接照搬历史问题。本次未做全仓逐行安全审计或亿级规模压测，也未修改实现、源 CSV、数据库或发布资产。
